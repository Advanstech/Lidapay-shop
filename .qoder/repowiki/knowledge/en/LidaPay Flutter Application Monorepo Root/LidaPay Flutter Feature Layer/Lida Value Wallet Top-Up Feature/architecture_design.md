Three-layer layout inside the feature:
- `providers.dart` exposes a single Riverpod `StateNotifierProvider.autoDispose<LidaValueTopupNotifier, LidaTopupState>` that orchestrates two funding paths — `lidaValueUse` (one POST `/lida-value/use` that debits and delivers in one call per the handoff contract) and `lidaValueSend` (wallet debit via `sendLidaValue`, then delivery through the shared `deliverPendingPayment` helper from `../payments`). It also defines the `ServiceFunding` enum (`momo`, `lidaValueUse`, `lidaValueSend`) used to route purchase funding.
- `data/lv_attempt_store.dart` persists an in-flight `LvAttempt` (draft + service type + optional `debitReference`) to `SharedPreferences` under key `lidapay.lv_attempt.v1`. On construction the notifier calls `resumePendingDelivery()` to finish only the delivery without re-debiting after process death.
- `screens/` holds the UI: `lida_value_screen.dart` renders the LV balance card, Use/Send/Sell/Convert action pills, history list, and bottom-sheet choosers; `convert_screen.dart` is the dedicated Convert page accepting `type:address` destinations (`momo:` and `bank:`).

Dependency direction is one-way: screens depend on providers; providers depend on `ServicesRepository` (from `../services`) and the local `LvAttemptStore`; nothing in this module is imported by other features except its own screens/providers. The feature consumes shared domain types (`PendingPayment`, `ServiceReceipt`, `ApiException`) and the payments module's `deliverPendingPayment` helper rather than reimplementing delivery logic.
