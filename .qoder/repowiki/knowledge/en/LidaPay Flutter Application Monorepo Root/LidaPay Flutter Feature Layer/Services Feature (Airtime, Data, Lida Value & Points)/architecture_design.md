Standard Riverpod feature split into three sub-packages with strict dependency direction screens → providers → data/repository → core network:
- `data/` defines the `ServicesRepository` abstract contract in `services_repository.dart`, its live implementation `RemoteServicesRepository` (which calls `ApiClient` against `/api/v1/reloadly/*`, `/lida-value/*`, `/lidapoints/*`, `/users/*`, `/api/v1/gtpay/*`), a `MockServicesRepository` for tests, and shared `Equatable` domain models in `service_models.dart`.
- `providers.dart` is the single entry point: it wires `servicesRepositoryProvider` to the session via `authSessionProvider` so GTPay payments are attributed to the signed-in user, exposes one `FutureProvider` per repository method (`ghanaNetworksProvider`, `countriesProvider`, `gtPayServicesProvider`, `lidaValueProvider`, etc.), plus a `StateNotifierProvider.autoDispose<LidaPointsHistoryController>` that implements paginated, deduplicated scrolling for the points ledger using `AsyncValue`.
- `screens/` holds the user-facing pages (`airtime_screen.dart`, `redeem_screen.dart`, `rewards_screen.dart`, `service_transaction_screen.dart`, `services_screen.dart`) which consume providers through `ConsumerWidget`/`ConsumerStatefulWidget`.
- `widgets/` contains reusable UI pieces (amount chips, phone formatter, country flag badge, receipt screen, wizard helpers, Lida Value checkout switch) consumed by the screens.
Dependency direction is strictly screens → providers → data/repository → core network; screens never import `ApiClient` directly.
