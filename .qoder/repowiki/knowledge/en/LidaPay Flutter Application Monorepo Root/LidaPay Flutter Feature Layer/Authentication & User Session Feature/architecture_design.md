Three-layer Riverpod feature module with strict dependency direction screens → providers → data.
- `data/auth_repository.dart` declares the `AuthRepository` abstract contract plus the `AuthSession` value object (tokens + `UserProfile`). Two implementations: `RemoteAuthRepository` calls `ApiClient` against `/api/v1/users*` and `/api/v1/auth/*`, persists tokens/profile via `TokenStore`, and decodes JWT `sub`/`userId` to backfill missing user ids; `MockAuthRepository` injects latency/failure for tests.
- `providers.dart` is the single wiring point: `authRepositoryProvider` returns `RemoteAuthRepository` (swappable at the top of the file), `authSessionProvider` exposes a `StateNotifierProvider<AuthNotifier, AuthSession?>` that owns session lifecycle — cold-start restore, OTP challenge flow (`_pendingOtpChallenge`, `_pendingOtpUsername`), biometric login, profile refresh with one delayed retry on transient errors, and logout hooks into `PushNotificationService`. Derived providers `hasSessionProvider` and `profileSyncProvider` are consumed by the router and profile screens.
- `screens/` contains one screen per flow (`login_screen.dart`, `register_screen.dart`, `otp_verification_screen.dart`, `forgot_password_screen.dart`, `reset_password_screen.dart`, `change_password_screen.dart`, `verify_password_change_screen.dart`); they are pure `ConsumerStatefulWidget`s that call methods on `ref.read(authSessionProvider.notifier)` and never import `ApiClient` or `TokenStore` directly.
- `widgets/password_requirements_panel.dart` is a shared UI helper implementing the five LidaPay password policy rules.
Dependency direction is strictly screens → providers → data; the live/mock switch is a single provider swap at the top of `providers.dart`.
