Organized as a standard Riverpod feature module with three layers:
- `data/` defines the `DashboardRepository` abstract interface (`dashboard_repository.dart`) plus two implementations: `RemoteDashboardRepository` (calls `ApiClient` against `/users/wallet/user`, `/lida-value/balance`, `/users/points`, and merges ledger + Lida Value + shop orders via `ActivityFeed`) and `MockDashboardRepository` for tests/dev.
- `providers.dart` is the single entry point that wires `dashboardRepositoryProvider` to `RemoteDashboardRepository` using the current `authSessionProvider` user id, then exposes `FutureProvider`s for `walletSummary`, `recentTransactions`, `flashDeals`, plus `StateProvider`s for UI state (`balanceHidden`, `deadTopupRefs`, `trackedPendingTopups`, `activeWaitingTopupOrderId`, `recentlySettledTopup`). It also hosts the long-lived `pendingRecipientTopupsProvider` `StreamProvider.autoDispose` that polls `GET /topups/{id}/status` with exponential backoff (4s → 60s) until terminal, blacklisting 404'd references in `deadTopupRefsProvider`.
- `screens/dashboard_screen.dart` composes the sliver-based layout and delegates rendering to leaf widgets under `widgets/` (`wallet_card`, `pending_topups_card`, `services_rail`, `flash_deals_carousel`, `transaction_tile`, `quick_actions`).
Dependency direction is one-way: screen → providers → repository → ApiClient; models in `dashboard_models.dart` are pure data classes extending `Equatable`. The module depends outward on `core/network`, `auth/providers`, `shop/providers`, `recipient_choice/providers`, and `notifications/providers` but has no reverse dependencies.
