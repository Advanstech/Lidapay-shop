Three-layer layout inside the feature:
- `providers.dart` exposes Riverpod state (`lidaValueTopupProvider`) built on a `StateNotifier<LidaTopupState>` that orchestrates two flows — `lidaValueUse` (single POST `/lida-value/use` debits + delivers in one call) and `lidaValueSend` (wallet debit via `sendLidaValue` followed by the standard provider delivery through `deliverPendingPayment`). It also defines the `ServiceFunding` enum (`momo`, `lidaValueUse`, `lidaValueSend`) used to route purchase funding.
- `data/lv_attempt_store.dart` persists an in-flight `LvAttempt` (draft + service type + optional `debitReference`) to `SharedPreferences` under key `lidapay.lv_attempt.v1`. This is the idempotency/retry backbone: after process death the notifier calls `resumePendingDelivery()` on construction to finish only the delivery without re-debiting.
- `screens/` holds the UI: `lida_value_screen.dart` renders the LV balance card, Use/Send/Sell/Convert action pills, history list, and bottom-sheet choosers; `convert_screen.dart` is the dedicated Convert page accepting `type:address` destinations (currently `momo:` and `bank:`).

Dependency direction is one-way: screens depend on providers; providers depend on `ServicesRepository` (from `../services`) and the local `LvAttemptStore`; nothing in this module is imported by other features except its own screens/providers. The feature consumes shared domain types (`PendingPayment`, `ServiceReceipt`, `ApiException`) and the payments module's `deliverPendingPayment` helper rather than reimplementing delivery logic.
