Organized as a classic Riverpod feature module with three layers:
- `data/` defines the `AuthRepository` abstract contract plus two implementations: `RemoteAuthRepository` (live calls via `ApiClient` against `/api/v1/users*` and `/api/v1/auth/*`, persisting tokens/profile through `TokenStore`) and `MockAuthRepository` (latency + failure injection for tests).
- `providers.dart` wires the repository via `authRepositoryProvider`, exposes the `AuthSession?` state through `authSessionProvider` (`StateNotifierProvider<AuthNotifier>`), and derives derived providers like `hasSessionProvider` and `profileSyncProvider`. `AuthNotifier` owns the session lifecycle — cold-start restore, OTP challenge flow, biometric login, profile refresh with retry-on-transient-error, and logout hooks into push notification service.
- `screens/` contains one screen per flow (`login_screen.dart`, `register_screen.dart`, `otp_verification_screen.dart`, `forgot_password_screen.dart`, `reset_password_screen.dart`, `change_password_screen.dart`, `verify_password_change_screen.dart`); they are pure `ConsumerStatefulWidget`s that read/write only through the Riverpod providers.
- `widgets/password_requirements_panel.dart` is a shared UI helper implementing the five LidaPay password policy rules.
Dependency direction is strictly screens → providers → data; screens never import `ApiClient` or `TokenStore` directly. The live/mock switch is a single provider swap at the top of `providers.dart`.
