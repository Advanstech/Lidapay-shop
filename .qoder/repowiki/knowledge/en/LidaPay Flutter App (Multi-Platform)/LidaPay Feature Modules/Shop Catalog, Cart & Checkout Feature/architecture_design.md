The module follows a clean-layered Riverpod feature pattern with three sub-folders:
- `data/` defines the `ShopRepository` abstract interface (one method per REST endpoint under `/api/v1/shop/*`) plus two implementations: `RemoteShopRepository` (HTTP via `ApiClient` + `ApiEndpoints`, with resilient JSON parsing through `payloadPool`/`stringField`/`numberField` candidate-key lists) and `MockShopRepository` (in-memory catalog with artificial latency).
- `providers.dart` is the single entry point that wires the repository via `shopRepositoryProvider` (currently bound to `RemoteShopRepository`), exposes Riverpod providers (`FutureProvider` for categories/products/orders, `StateNotifierProvider` for cart and loved-products, `StreamProvider.autoDispose.family` for live order tracking polling every 8s), and owns business state in `CartController` (idempotent checkout with recovery of partially-created orders) and `OrdersController` (paginated orders with sentinel-row logic).
- `screens/` contains the four top-level screens (`shop_screen`, `cart_screen`, `orders_screen`, `checkout_success_screen`) which consume only the Riverpod providers — they never call the repository directly.
- `widgets/` holds reusable UI pieces (product card/detail sheet, shipping address picker, delivery pin screen, driver location map) consumed by the screens.
Dependency direction is strictly one-way: screens → providers → repository → API; widgets have no data-layer dependencies. The mock/live boundary is a single provider swap at `shopRepositoryProvider`.
