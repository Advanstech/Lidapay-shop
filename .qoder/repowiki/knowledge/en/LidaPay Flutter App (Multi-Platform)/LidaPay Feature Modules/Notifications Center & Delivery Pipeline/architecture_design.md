Three-layer layout inside `lib/features/notifications/`:
- `data/notification_models.dart` defines the immutable `AppNotification` value object (Equatable) with an `fromApiJson` factory that normalizes many backend field shapes (`type` vs channel dispatches, nested `data`/`payload`/`meta`, `_id`/`$oid`) into a single model, plus `kind` classification (`decision|resolved|airtime|data|order|wallet|security|promo|general`).
- `data/notifications_repository.dart` declares the `NotificationsRepository` abstract interface; `remote_notifications_repository.dart` implements it against `ApiClient` + `ApiEndpoints.notifications`; `mock_notifications_repository.dart` provides test fixtures. The repository is the only place that touches Dio/API.
- `providers.dart` wires Riverpod: `notificationsRepositoryProvider` swaps mock/live via one Provider, `rawNotificationsProvider` fetches via the repo, `readNotificationsProvider` (StateNotifier over `SharedPreferences`) persists per-user read IDs keyed by `lidapay.read_notifications.<userId>` with legacy-key migration, `dismissedNotificationsProvider` holds in-memory optimistic dismissals, and `notificationsProvider` composes raw data + read + dismissed + active user to dedupe same-kind/same-body alerts within a 10-minute window and merge cross-channel ids.
- `screens/notifications_screen.dart` is the sole UI consumer — a `ConsumerWidget` that reads `notificationsProvider` / `unreadNotificationsProvider`, renders cards with swipe-to-dismiss, and opens a bottom-sheet detail view that routes based on `notification.kind`.
Dependency direction is strictly screens → providers → data layer; the screen never imports `ApiClient` or `SharedPreferences` directly.
