Three-layer leaf module organized by concern:
- `legal_content.dart` is the data layer: defines the immutable `PolicySection` / `PolicyDocument` models, holds all six policy texts as top-level `const` instances (`privacyPolicy`, `termsOfService`, `paymentsRefundPolicy`, `kycAntiFraudPolicy`, `accountDeletionPolicy`, `aboutLidapay`), exposes a single `allPolicyDocuments` list plus a `policyDocumentById` lookup, and publishes `kCurrentPolicyVersion` (bumped when text changes meaningfully) together with support/contact constants and an `accountDeletionRequestUri` mailto helper.
- `policy_acceptance.dart` is the state layer: a Riverpod `AsyncNotifierProvider<PolicyStatusNotifier, PolicyAcceptance?>` persists the accepted version and timestamp in `SharedPreferences` under `_versionKey`/`_acceptedAtKey`; `PolicyAcceptance.isCurrent` compares against `kCurrentPolicyVersion`, and `policyAcceptedSync` provides a synchronous SharedPreferences read for form-gating paths that cannot await providers.
- `screens/` contains the UI: `legal_hub_screen.dart` lists every document from `allPolicyDocuments`, shows a sticky review banner when the stored version is stale, and navigates via `go_router` to `${AppRoutes.legal}/${doc.id}`; `legal_document_screen.dart` is a generic branded renderer for any `PolicyDocument` with a sticky hero header, last-updated chip, and numbered sections.

Dependency direction is one-way: screens → `legal_content.dart` + `policy_acceptance.dart`; the content layer depends only on `core/constants/app_constants.dart` (for `AppConstants.appVersion`) and has no UI or persistence coupling. The hub maps each document id to a `(IconData, List<Color>)` gradient tuple via a local `_meta` map rather than importing per-document metadata.
